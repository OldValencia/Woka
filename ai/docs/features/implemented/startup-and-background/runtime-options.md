# Woka: варианты runtime, быстрый запуск и низкая RAM

**Дата:** 2026-11-19. **Версия:** исследование для 1.0.8.
**Статус:** сохранённое обсуждение, выбор архитектуры не сделан. Продолжить изучение позже;
этот документ не означает разрешения на миграцию UI/runtime или подключение новых зависимостей.

Основной план — [startup-and-background](startup-and-background.md).
Результаты проведённых экспериментов, команды и артефакты — [ST-001](tickets/ST-001-startup-measurements.md).

## Требования автора

- Один разработчик; сохранить Kotlin и общую кодовую базу для Windows, Linux и macOS.
- Предпочтительно одно приложение, без отдельного интерфейса под каждую ОС.
- Желаемый запуск до полезного изображения — 100–200, максимум 300 мс; пустое окно не считается.
- Минимальное потребление RAM, особенно после закрытия. Постоянный фон на 100–200 МБ
  пользователь считает неприемлемым компромиссом.
- Автор наблюдал около **460 МБ** после открытия Woka, не открывая файл вручную.
  Это наблюдение пользователя, а не установленная причина или измеренный состав памяти.
- В последнем сообщении автор попросил сохранить обсуждение и ссылку в next_steps, затем
  продолжить исследование позже. Не запускать новые эксперименты в рамках этого сохранения.

## Что уже измерено

| Сценарий | Результат | Ограничение |
|---|---:|---|
| AppCDS, до параллельной загрузки FFmpeg | JPEG ~802 мс | Новый процесс, тёплый файловый кэш |
| AppCDS + media prewarm | JPEG ~689 мс; финальная сборка ~692 мс | Медианы 3 запусков через EXE |
| AOT class linking + media prewarm | JPEG ~612 мс | Эксперимент; в packaged defaults не включён |
| AOT: Xms по умолчанию → Xms32m | Peak Private Bytes ~915→440 МиБ | JPEG открыт; это не idle RAM |
| Тот же Xms эксперимент | Working Set ~301→291 МиБ | Физическая память снизилась гораздо меньше |

Метрика первого кадра — завершение CPU draw submission, не точный GPU scan-out.
Первое обучение AppCDS по-прежнему дорогое: в финальной серии JPEG ~8,8 секунды.
Сборка и 1689 тестов прошли. Подробный checkpoint находится в ST-001.

**Нельзя обещать 100–300 мс на основании этих измерений.** Настоящий cold-filesystem запуск,
медленный диск, сложный файл и первый запуск после обновления — отдельные сценарии.

## Сначала объяснить 460 МБ

Память процесса включает Java heap, классы/JIT, стеки потоков, AWT, Skia, графические
ресурсы, native libraries и медиакэши. Пока нет измерения, нельзя назначать виновником JVM,
AWT или cache. Xmx — не размер всей памяти процесса.

- Сравнить чистый Welcome с изолированным storage и обычный запуск с восстановлением папки.
  Сейчас запуск без аргументов может открыть последнюю либо первую linked folder, а значит,
  начать работу с миниатюрами без ручного открытия файла.
- Снять heap used/committed, физическую и приватную память процесса, данные о JVM/native
  allocations и графических ресурсах; отдельно измерить реально удерживаемые bitmap-кэши.
- У ImageBitmapCache **лимит** 256 МиБ; это не заранее выделенный блок, retainedBytes начинается с нуля.
- Не смешивать цифры разных столбцов Диспетчера задач. Вытеснение страниц working set не
  равнозначно освобождению ресурсов; возвращение вытесненных страниц тоже имеет стоимость.
- Малый Xms и возврат свободного heap ОС проверять по одному изменению, затем проверять
  playback/GC на 4K/8K. Снижение commitment не объявлять таким же снижением физической RAM.

## Рассмотренные варианты

| Вариант | Что сохраняем | Оценка и что проверить |
|---|---|---|
| Текущий HotSpot, управление ресурсами и настройки | Весь продукт | Первый шаг с минимальным риском; эффект ещё измерить |
| OpenJ9 | Kotlin/Compose, если совместимы зависимости | Сравнить память и запуск; проверить Java 25, FFM, Skiko, JavaCV и целевые платформы |
| GraalVM Native Image с AWT | Kotlin и значительную часть нынешнего UI | Основной кандидат на compatibility probe; изучить Liberica NIK |
| Native Image + Tao под Compose | Kotlin и Compose-компоненты | Более глубокая смена оконного слоя; исследовать Nucleus и стоимость сопровождения |
| Фоновая JVM без окна / сохранённое окно | Текущий runtime и UI | Повторное открытие, не холодный старт; RAM ещё не измерена, приоритет автора против тяжёлого фона |
| Отдельный native viewer + полноценная Woka | Часть движка и основное приложение | Рабочая схема, но второй UI, handoff и синхронизация поведения увеличивают работу одиночного разработчика |

### Native Image и JEP 483 — разные вещи

JEP 483/AOT class linking ускоряет загрузку и связывание классов в JVM.
Native Image заранее компилирует достижимый код в машинный, оставляя необходимый runtime
и GC, без обычного запуска HotSpot/JIT. Kotlin при этом можно сохранить.

Документация Nucleus описывает native image для Compose и сборки на каждой целевой ОС.
Liberica NIK документирует native AWT/Swing на Windows/Linux/macOS. Это свидетельство
наличия подхода, **не** подтверждение совместимости или скорости Woka.

Наши существенные проверки: Compose/Skia, JavaCV/JavaCPP/JNI, FFmpeg, FFM-мосты DV/JXL/JXR/RAW,
reflection/resources и загрузка DLL. GraalVM 25 требует регистрации foreign-call descriptors
при сборке. Его таблица FFM включает Windows/x64, Linux/x64, Linux/AArch64, macOS/AArch64;
поддержку других архитектур нужно проверять отдельно.

### Замена AWT — отдельный эксперимент

Nucleus предлагает Tao как оконный backend под Compose. Это позволяет исследовать замену
создания окон, event loop и представления GPU surface, сохраняя Compose-компоненты.
Не означает бесплатной миграции: адаптировать/проверить окна, PiP, диалоги, drag-and-drop,
clipboard, ввод, DPI, полноэкранный режим, accessibility и интеграцию с ОС.

Nucleus — сторонний проект; оценить API, зависимости, поддержку ОС и устойчивость обновлений.
Native Image сначала сравнить при неизменном оконном слое, затем отдельно оценить Tao.
Чужие рекламные показатели RAM/старта не переносить на Woka.

### «МикроJVM» и ручное управление памятью

Готовая «микроJVM», доказанно совместимая со всем стеком Woka, не найдена. OpenJ9 —
проверяемый кандидат, но не обещание нескольких мегабайт памяти или 100 мс до изображения.
Ни другой runtime, ни Native Image сами не устраняют native buffers и графические поверхности.

Ручной контроль полезен для принадлежащих нам ресурсов: остановка и join декодеров,
освобождение native buffers/bitmap после прекращения их использования UI, ограничение кэшей,
ленивая загрузка подсистем. Обычные Kotlin/JVM-объекты по-прежнему управляются GC.
Сохранение Kotlin не мешает явному управлению native lifetime.

## С чего продолжить

1. Профиль памяти текущей Woka: чистый Welcome, восстановленная папка, JPEG, закрытие файла.
   Установить владельцев памяти и отдельно подтвердить наблюдение ~460 МБ.
2. Устранить измеренные ненужные allocations/удержания; проверить малый Xms без потери playback.
3. Маленький Native Image compatibility probe на **реальном стеке Woka**:
   окно Compose/Skia → JPEG → FFmpeg/первый видеокадр → DV FFM. Не ограничиваться пустым демо.
4. При успешной совместимости измерить запуск/RAM и прогнать функциональные проверки.
   Отдельно оценить наличие рабочих сборок для Windows/Linux/macOS.
5. Только при необходимости проверить Tao и сравнить его с AWT на одинаковом сценарии.
6. Выбрать архитектуру по результатам и цене сопровождения. Не начинать переписывание
   всего продукта или второй viewer до этого сравнения.
