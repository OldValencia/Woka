# Editor — first hands-on review, 2026-08-18

The author ran the editor for the first time after ME-106 and reported six things. **Recorded, not
acted on**: nothing here is implemented, and item 1 overturns a settled design decision rather than
extending it, so it needs working through before any of it becomes a ticket.

Each item below is what was said, then what it collides with in the tree as it stands.

---

## 1. The save model is wrong — and one defect underneath it

### What was reported

> Сначала я подумал, что ничего не сохраняется. Вышел из изначальной картинки — увидел в Grid сначала
> одну, а потом после перезахода ещё несколько картинок (я несколько раз вносил изменения).

Two separate things in that sentence, and they must not be conflated:

**(a) A defect.** Saves did not appear in the grid when they happened. One picture showed up; the rest
only after leaving and re-entering the folder. ME-106 calls `viewModel.refresh()` on `onSaved`, so
either that is not firing, is firing before the write lands, or the listing is not re-read the way it
is assumed to be. **Unverified** — no diagnosis was attempted, and it should be instrumented rather
than guessed at (`EditorHost`'s `done` runs the save in a `rememberCoroutineScope()` whose composition
`onClose()` then disposes; that is the first suspect and nothing more than a suspect).

**(b) The design.** Every save minting a new file is not what was wanted at all.

### What is wanted instead

> Я хотел, чтобы картинка в себе хранила исторические данные, как в iOS редакторе. Чтобы было две
> версии у картинки ВНУТРИ себя без создания ещё одной картинки — отредактированная и оригинал.
> Отредактированную мы можем сколько угодно менять, новых экземпляров не должно создаваться. И в любой
> момент у тебя должна быть возможность вернуться к оригиналу.

So: **one file, two versions inside it** — the edit and the original. Editing repeatedly replaces the
edited version rather than adding a file. Revert to original available at any time.

### What this collides with

This is the **direct reversal of §5 and of two decision-log rows**, not an addition to them:

| Settled | Date | Now contested |
|---|---|---|
| "**There is no hidden backup store.** The original is preserved by not being written to." (§5) | — | the original would now be stored *somewhere* |
| "Backups? **None.** Save a Copy is the default; overwrite is explicit and confirmed" | 2026-08-16 | |
| "~~ME-107 — Revert to Original~~ — dropped. There is no backup store to revert from" | — | the dropped ticket is the requested feature |

§5's argument against a backup store was specific and is still on the table: a hidden `.originals`
directory means an index to keep consistent, orphans to sweep, and a promise that breaks the moment the
folder moves to another machine. **"Inside the picture itself" is a different proposal and may dodge
all three** — which is exactly why it needs designing rather than assuming either way.

### The open questions, none of which should be guessed

- **Where does "inside" actually live?** A JPEG can carry an APP segment; PNG has ancillary chunks;
  WebP has RIFF chunks. Storing a *whole original* inside the edited file roughly doubles its size.
  Storing the **document** instead — the `EditDocument` is a few hundred bytes and is serialisable by
  construction (§3.1) — means the original is reconstructed by *replaying nothing*, i.e. the file on
  disk stays the original and the edit is applied on read. That is a genuinely different architecture
  from what ships today and is closer to what iOS actually does.
- **What does the grid and the viewer show** — the edited version, presumably. Then every reader in
  the app has to know about the sidecar/segment, not just the editor.
- **What happens when the file is opened by anything that is not Woka?** iOS's answer is that the
  rendered file *is* the edit and the original is kept alongside in its own store. Woka's linked
  folders are the user's own directories, which is the constraint §5 was written against.
- **Does `Save a Copy` survive at all**, as an explicit action rather than the default?

## 1b. The editor appears instantly, with no transition

Said inside item 1 but a separate request:

> Переход от Viewer к Editor хотелось бы сделать более плавным. Как и от Grid к Editor. Потому что
> например переход от Grid к Viewer происходит с анимацией. Так как Editor находится в правой части
> нашего дока — логично было бы сделать так, чтобы происходила анимация свайпа вправо.

Grid → Viewer animates; Grid → Editor and Viewer → Editor do not — the overlay simply appears, because
ME-106 mounts it with a bare `editorTarget?.let { … }` and nothing else.

The proposed shape is **a swipe from the right**, on the reasoning that `Editor` sits to the right in
the dock, so entering it should read as moving rightward and leaving it as moving back left. That gives
the app a spatial model rather than a fade, and it applies to both doors.

Worth checking against what Grid → Viewer already does before inventing a second animation language:
whatever that transition is, the editor's should be its sibling, not a new idea.

## 2. The top bar shows a folder path, and it is useless

> Сверху остаётся путь к папке. Только он бесполезен. Зачем его там писать? Если можно перенести туда
> название редактируемого файла. Мы же так делаем уже с Video Viewer. Сделай так же и с Editor —
> зачем нам видеть путь к папке. Тем более по нажатии на неё ничего не происходит.

The app shell's `SmartBreadcrumbs` stays visible above the editor, showing the folder path, and clicking
it does nothing while the editor is open. The video viewer already replaces that region with the file's
name; the editor should do the same.

`EditorTopBar` *does* draw the file name — so this is about the **shell's** top bar above it, not the
editor's own, and the fix is in the same place that hides the dock (`TopBarAccessories` /
`LocalDockAccessories`).

## 3. Zoom does nothing

> Зум ничего не делает. А надо бы.

Correct and deliberate: v1 is `Fit` only, decided 2026-08-18 (§9), because above 100 % the canvas draws
the ≤2560 px proxy and zoom without ME-116's native-region draw would ship visibly blurred.

**The decision may want revisiting** now that it has been felt rather than reasoned about — a wheel that
does nothing reads as broken, which is worse than one that is slightly soft. Options are to bring ME-116
forward, or to ship zoom capped at 100 % where the proxy is still sharp.

## 4. The eye and Edit buttons stay visible

> Кнопки глазика и Edit надо скрывать при открытии Editor.

`GlobalControlButtons` — the info, carousel-eye, PiP and `Edit` controls — belong to the viewer's chrome
and remain on screen with the editor over them. The dock is hidden (ME-106) and these were missed.
`Edit` in particular is live while already editing.

## 5. The Transform panel is far too wide

> Само окно Transform неизвестно зачем очень и слишком широкое. Кнопка Reset располагается на
> расстоянии ещё 3х таких же кнопок Rotate left от неё. Короче там куча пустого пространства.

`EditorTokens.Inspector.width` is a fixed **420 dp**, chosen so the card does not resize when the tool
changes — "a card that grew per tool would move the rail under the cursor every time the tool changed".
For a tool with four small buttons that leaves most of the card empty.

The tension is real: fixed width buys a stable rail position, and costs this. Worth reconsidering —
possibly a minimum rather than a fixed width, or action rows that lay out as a compact button group
instead of one label column plus one control column.

Related and probably the same fix: `ActionParamRow` currently draws the label in the left column **and**
as the button's own text, so "Rotate left" appears twice on the row.

## 6. `Cancel` duplicates the Back button

> Зачем нам кнопка "Cancel" если у нас есть кнопка Back сверху? Может интегрировать в неё всё так же,
> как мы сделали и в Video Viewer? Зачем нам дублировать кнопки, мы можем просто их функционал
> переопределить. А то сейчас кнопка Back выходит из папки. Зачем-то.

Two problems at once. The editor adds its own `Cancel` while the shell's Back button is still there —
and Back still **navigates out of the folder**, which is actively wrong: with an editor open it should
leave the editor, exactly as the video viewer redefines it rather than adding a second control.

So: drop `Cancel` from `EditorTopBar`, and make Back mean "leave the editor" while one is open,
including the dirty-document confirmation currently wired to `Cancel`.

---

## Nothing here is committed or implemented

Items 2, 4, 5 and 6 are contained UI work and could become one ticket between them — they are all "the
shell around the editor is not yet aware the editor exists".

Item 3 is a decision to revisit, not a bug.

**Item 1 is a design change** to the feature's central promise, and it invalidates ME-104's and ME-130's
premises as written. It should not be turned into a ticket until the questions above have answers.
